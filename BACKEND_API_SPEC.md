## 2. `GET /api/v1/search` — filters

The deployed endpoint accepts `cameras`, `scenes`, `tags` (all repeatable), `min_confidence` (0–100), `date_from` and `date_to` (`date`).

### 2.1 Apply the filters inside the RAG (**RAG**)

Per the backend's OpenAPI description, the filters are applied **after** retrieval and enrichment, because `rag.pipeline.answer_query()` has no filter parameters. The result: a filtered search can return fewer than `limit` moments, or none, even when matching footage exists further down the ranking. The `answer` summary is also written over the unfiltered set, so it can describe moments that were filtered out.

**Request:** pass the filters to the RAG as metadata filters (`videos.camera_id`, `videos.scene`, tags, score), so retrieval ranks only matching moments and the `answer` describes what is returned. Until then, a cheap mitigation is to over-fetch from the RAG (e.g. `limit × 5`) before filtering.

### 2.2 Date filters — videos with an unknown time zone

`date_from` / `date_to` filter on each result's `timestamp`, which the backend builds as `bronze.videos.capture_start_local` + `start_seconds` in the video's `capture_time_zone` (`_build_timestamp` in `app/services/rag_client.py`). **Correction to earlier versions of this spec:** a moment's wall-clock time does exist; it is only missing when the time zone is unknown.

The catch: `capture_time_zone` is literally `"unknown"` for at least some videos, so their `timestamp` is `null`, and **any date filter silently excludes them**, even when their footage is inside the range. **Request:** fill in the time zone (MEVA was recorded at one facility, so it's one zone for every video), or return how many results a date filter excluded for lack of a time, so the UI can say so. The frontend will wire the From/To range once this is settled.

### 2.3 Frontend: send the filters (**frontend work**)

`searchClips()` in `src/lib/api/endpoints.ts` still sends only `q` and `limit`. The Filters modal (camera, scene, event type, minimum confidence) and the inline term menus set filters the request ignores. Wire them as repeatable params.

### 2.4 Citations in the `answer` — `[n]` must map to a result (**RAG**)

**How it works today.** The RAG's prompt numbers the retrieved events and tells the LLM to _"Cite each event you use by its number, like [1] or [3]"_ (`_SYSTEM_PROMPT` in `rag/pipeline.py`). So `[n]` in `answer` means the n-th of the RAG's `sources`, 1-based, best match first. `/assistant/ask` doesn't do this: it returns `citations: [{ moment_id }]` and strips its own `CITED:` line.

**The problem: the numbers can point at the wrong result.** Between the RAG and the response, `rag_client.query()` drops sources:

1. `sources[:limit]` cuts the list;
2. sources whose `event_id` no longer exists in bronze are dropped (`_to_item` returns `None`);
3. sources that fail the filters are dropped (§2.1).

Positions shift after any drop. If the RAG's source 2 is dropped, the result that `answer` calls `[3]` becomes the second item in `results`. The frontend can only map `[n]` by position, so every citation after the gap points at the wrong moment, or at nothing.

**Request:**

- **Add `citation_index: int` to each `RagResultItem`:** its 1-based position in the RAG's `sources`, **set before any drop** and never renumbered. The frontend already reads it (`RagResultItem.citation_index` → `Clip.ref`) and falls back to the position only while it's missing.
- **Handle citations of dropped sources.** Either remove `[n]` markers for sources that aren't in `results` from `answer`, or leave them: the frontend shows a `[n]` with no matching result as plain text, not as a chip.
- **Keep the numbering scheme stable:** 1-based, `[n]` or `[n, m]`, never inside code or links. Document any change to the prompt's citation format, since the frontend parses it (`src/lib/citations.ts`).
- **Optional:** `/assistant/ask` could also cite inline with the same numbers (the moments carry them), so follow-up answers read like the search summary. Today its citations only appear as chips under the answer.

**What the frontend shows (simulated until `citation_index` exists):** each `[n]` in the answer is a numbered chip that opens that moment; the cited moments are listed under the answer as **Sources** with the same numbers.

## 4. Timestamps as ISO 8601 — please confirm

Both fields are plain strings in the schema, so the format isn't guaranteed:

- `RecentQueryOut.ts`: shown relative to now ("10 min ago", then "Sep 21" after a week). A value without an offset is read as UTC; anything that isn't ISO is shown as-is.
- `SavedQueryOut.savedOn`: ISO is formatted as `Sep 24`; anything else is shown as-is.

## 5. `GET /api/v1/videos/{video_id}/tracks` — box origin

The frontend draws `x`, `y` as the box's **top-left corner**, in source-frame pixels (`frame_width` × `frame_height`). **Please confirm.** If the backend sends the centre instead, every box is offset by half its size.

## 6. Video URLs — signed and seekable

`video_url` is loaded by a plain `<video>` element, which can't send the bearer token. It must be public or a **signed URL** that expires. `bronze.videos` has `storage_bucket` and `storage_path`, so the backend can sign a URL per request (for example with Supabase Storage `createSignedUrl`). The file host must allow HTTP range requests, and MP4s should be encoded with `-movflags +faststart`; otherwise seeking to `start_seconds` waits for most of the file to download.

## 7. Schema cleanup

- **`perspective`** is still in `Clip` and `CameraDirectoryEntry`. It isn't in the database and the frontend ignores it. Drop it.
- **Fill `thumbnailUrl` in `Clip`** (`GET /clips/{id}`, `/clips/{id}/related`). `clip_builder.py` sets it to `None`, although the public `GET /clips/{id}/thumbnail.jpg` already serves every event. Until then the frontend builds that URL from the id (`clipThumbnailUrl` in `src/lib/api/normalize.ts`).
- **Keep thumbnails across deploys.** The frame cache lives on Render's ephemeral disk, so after every deploy (and every free-plan restart) each thumbnail costs 1–6 s again, and a results page fires up to 10 extractions at once on a small instance. Storing the JPEGs in Supabase Storage (or R2, where the videos already are) once, on first extraction, removes both problems.
- **Keep `timestamp`** in `RagResultItem`. An earlier version of this spec asked to drop it as "not in the database"; that was wrong (see §2.2). The frontend doesn't show it yet.

## 9. RAG improvements (optional / proposed)

### 9.1 `POST /api/v1/assistant/suggestions` generated by the RAG

Today the backend builds the opening questions **from rules, not the RAG/LLM**. The contract doesn't change, so moving to RAG-generated suggestions needs no frontend work. Requirements when that happens:

- Suggest only questions the data can answer: no camera comparisons with one camera, no vehicle filters with no vehicles, nothing needing cross-camera re-identification, and no time comparisons for moments without a known time (§2.2).
- Skip questions already in `history`.
- Optional: `/search` could return `suggested_questions` next to `answer`, saving this call right after a search. The endpoint is still needed for moment selection and Clip Detail.

### 9.2 Cross-camera reasoning in `POST /api/v1/assistant/ask`

Questions like _"Show this vehicle's full path across cameras"_, _"Did anyone leave the building before this?"_ or _"Who else was near this location around this time?"_:

- **Time is partly available.** MEVA cameras are GPS-synchronised and each video's start is known (`capture_start_local`; the RAG also parses it from the file name, `absolute_window` in `rag/pipeline.py`), so "before/after" and "around this time" work across cameras at the same site. `/assistant/ask` doesn't use it yet: its moments carry only in-clip seconds, and its prompt tells the LLM there is no wall-clock time. **Request:** add the moment's absolute time to `AssistantMoment` and the prompt, where the time zone is known.
- **No re-identification link** across cameras, so "the same vehicle" can't be followed from camera to camera. Within one video, `bronze.objects` and `bronze.geometries` (bounding boxes, `spatial_position`) support it.
