## 2. `GET /api/v1/search`

The deployed endpoint accepts `q`, `limit`, `cameras`, `scenes`, `tags` (all repeatable), `min_confidence` (0–100), `date_from` and `date_to` (`date`).

### 2.1 Apply the filters inside the RAG (#1)

The filters are applied **after** retrieval and enrichment (per the endpoint's own description), because `rag.pipeline.answer_query()` has no filter parameters. A filtered search can therefore return fewer than `limit` moments, or none, even when matching footage exists further down the ranking. The `answer` is also written over the unfiltered set, so it can describe moments that were filtered out.

**Request:** pass the filters to the RAG as metadata filters (`videos.camera_id`, `videos.scene`, tags, score), so retrieval ranks only matching moments and the `answer` describes what is returned. A cheap mitigation meanwhile: over-fetch from the RAG (e.g. `limit × 5`) before filtering.

### 2.2 Date filters and unknown time zones (#2)

`date_from` / `date_to` filter on each result's `timestamp`: `bronze.videos.capture_start_local` + `start_seconds`, in the video's `capture_time_zone` (`_build_timestamp` in `app/services/rag_client.py`).

`capture_time_zone` is literally `"unknown"` for at least some videos, so their `timestamp` is `null`, and **any date filter silently excludes them**, even when their footage is in range. **Request:** fill in the time zone (MEVA was recorded at one facility, so it is one zone for every video), or report how many results a date filter excluded for lack of a time. The frontend wires its From/To range once this is settled.

### 2.3 Citations in the `answer`: send `citation_index` (#3)

The RAG's prompt tells the LLM to _"Cite each event you use by its number, like [1] or [3]"_, so `[n]` in `answer` is the n-th of the RAG's `sources`, 1-based. The frontend turns each `[n]` into a numbered chip that opens that moment, and lists the cited moments as **Sources**.

**The problem:** `rag_client.query()` drops sources before responding. It cuts them to `limit`, drops events missing from bronze (`_to_item` returns `None`), and drops those failing the filters (§2.1). After any drop, positions shift, and every citation after the gap points at the wrong moment or at nothing. The frontend can only map `[n]` by position today.

**Request:**

- **Add `citation_index: int` to each `RagResultItem`:** its 1-based position in the RAG's `sources`, **set before any drop** and never renumbered. The frontend already reads it (`RagResultItem.citation_index` → `Clip.ref`) and falls back to the position only while it is missing.
- **Citations of dropped sources:** remove those `[n]` markers from `answer`, or leave them; the frontend shows a `[n]` with no matching result as plain text.
- **Keep the format stable:** 1-based, `[n]` or `[n, m]`, never inside code or links. Tell the frontend about any change to the prompt's citation format, since `src/lib/citations.ts` parses it.

## 3. Clip thumbnails

### 3.1 Fill `thumbnailUrl` on `/clips/{id}` and `/related` (#4)

`app/services/clip_builder.py` still sets `thumbnailUrl=None`, although `GET /clips/{id}/thumbnail.jpg` serves every event. **Request:** return that URL, as `/search` already does for `thumbnail_url`. Until then the frontend builds it from the event id (`clipThumbnailUrl` in `src/lib/api/normalize.ts`).

### 3.2 Keep thumbnails across deploys and restarts (#5)

The extracted frames are cached on local disk (`thumbnail_cache_dir`). Railway's filesystem is ephemeral unless a volume is mounted, so after every deploy or restart each thumbnail costs 1–6 s again, and a results page fires up to 10 extractions at once. **Request:** store each JPEG once, on first extraction, in Supabase Storage or R2 (where the videos already are), or mount a Railway volume for the cache.

## 6. Video URLs (#8)

`video_url` is loaded by a plain `<video>`, which can't send the bearer token. Today the videos are on a **public** Cloudflare R2 bucket, which works. Two remaining points:

- **If the footage must be private**, return a short-lived signed URL per request instead of the stored one.
- **Seeking:** MP4s should be encoded with `-movflags +faststart`; otherwise seeking to `start_seconds` waits for most of the file to download.

## 7. Railway configuration: `PUBLIC_BASE_URL` (#9)

`/search` builds `thumbnail_url` from `PUBLIC_BASE_URL`, or from the request URL if it's unset. Behind Railway's proxy, the request URL can come out as `http://`, and an `https` site blocks those images as mixed content. **Please confirm** `PUBLIC_BASE_URL=https://surveillance-backend-production.up.railway.app` is set on Railway.

## 8. Optional and proposed improvements

### 8.1 Stream the answer's text (#10)

`POST /assistant/ask/stream` (in `main`) sends **progress, not the answer's text**: `event: status` steps (`{"phase", "message"}`, e.g. "Generating answer…"), then one `event: result` (the `AssistantAskResponse`) or `event: error` (`{"message"}`). The frontend reads it with `fetch` and a stream reader, shows each step in the thinking bubble, and falls back to `POST /assistant/ask` on a 404/405.

As the backend notes, `rag.llm.complete()` is one blocking call, so nothing arrives during the LLM's own wait. **Optional next step:** with a streaming LLM client, add `event: delta` (`{"text": "…"}`) chunks before `result`. The frontend's answer component already takes the text as it grows (`StreamedText`), so it would show the first words while the model is still writing; `result` would still carry the citations and suggestions.

### 8.2 `/assistant/suggestions` generated by the RAG (#11)

The opening questions still come from rules, but in `main` those rules read each event's real detections (object types, detection confidence) through `event_id`, and fall back to the caption without it. That already adds moment questions such as "Was anything left behind at this location?". Moving to RAG-generated questions needs no frontend change, as long as they:

- only suggest what the data can answer: no camera comparisons with one camera, no vehicle filters with no vehicles, no cross-camera re-identification, and no time comparisons for moments without a known time (§2.2);
- skip questions already in `history`.

Optionally, `/search` could return `suggested_questions` next to `answer`, saving this call right after a search.

### 8.3 Absolute time and cross-camera reasoning in `/assistant/ask` (#12)

- **Time is partly available.** MEVA cameras are GPS-synchronised and each video's start is known (`capture_start_local`; the RAG also parses it from the file name), so "before/after" and "around this time" could work across cameras at one site. `/assistant/ask` doesn't use it: its moments carry only in-clip seconds, and its prompt tells the LLM there is no wall-clock time. **Request:** add the moment's absolute time to `AssistantMoment` and to the prompt, where the time zone is known.
- **No re-identification link** across cameras, so "the same vehicle" can't be followed from camera to camera. Within one video, `bronze.objects` and `bronze.geometries` support it.

### 8.4 `GET /api/v1/search/stream`: progress for the first search (#16)

**Implemented in `main`** (`35aa17a`, `app/api/routes/search.py`), **not yet on Railway**: the deployed `/openapi.json` (checked 2026-10-03) has no such route. Same params as `/search`, same framing as `/assistant/ask/stream`: `status` steps `searching` → `thumbnails` → `saving`, then one `result` (the `RagQueryResult`) or `error` (`{"message"}`).

**Frontend:** wired. `searchClips()` reads it with `fetch` and a stream reader, shows each step in the thinking bubble and over the Matching Moments strip, and falls back to `GET /search` on a 404/405, which is what runs until the deploy. Two notes for the backend:

- **Not `EventSource`**, despite the route's comment: it can't send `Authorization: Bearer`, which the route requires.
- **Moments arrive with the summary**, in the one `result`, because `rag_query()` retrieves, enriches and writes the summary in one call. To draw the moments before the summary is written, split it with `retrieve()` / `generate_answer()` and send the enriched moments in their own event (e.g. `event: moments`) before `result`.
